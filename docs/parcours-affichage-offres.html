Parcours d'affichage des offres

Ce document suit une requête de la page React jusqu'à SQLite, puis le retour des données vers l'interface de Gesta.

1. Architecture générale

Gesta est un monorepo npm composé d'un frontend React/Vite et d'un backend Express/TypeScript. Le frontend ne lit jamais SQLite directement : il appelle l'API HTTP, tandis que le backend porte l'authentification, les permissions, les règles métier et les requêtes SQL. 

Navigateur
  → frontend React/Vite (http://localhost:5173)
  → proxy Vite : /api/offers → /offers
  → backend Express (http://localhost:3000)
  → contrôleur → service → repository
  → SQLite (backend/data/gesta.db)

2. Parcours de lecture des offres

Étape 1 — Routage et session

frontend/src/App.tsx appelle useAuth une seule fois. Si l'utilisateur est connecté et que canListOffers l'autorise, la route /offres rend OffersPage. Le token et logout lui sont transmis par props.

Étape 2 — Page et hook React

frontend/src/pages/OffersPage.tsx compose l'écran. Le hook frontend/src/hooks/useOffers.ts déclenche le chargement, conserve les états chargement/erreur/données et signale une session expirée à onUnauthorized.

Étape 3 — Service frontend et validation

frontend/src/services/offers.service.ts envoie une requête GET /api/offers avec le token dans Authorization. La réponse est contrôlée par un type guard et readJson dans frontend/src/utils/api.ts, puis convertie selon les modèles frontend.

Étape 4 — Proxy Vite et route Express

frontend/vite.config.ts retire le préfixe /api et transmet vers le backend. La route créée dans backend/src/controllers/offers.controller.ts exécute le middleware d'autorisation authorize(canListOffers), puis demande au service la liste visible par l'utilisateur authentifié.

Étape 5 — Règle métier de visibilité

backend/src/services/offers.service.ts choisit le filtre selon le profil : l'administrateur voit toutes les offres, l'étudiant les offres PUBLISHED, et le déposant les offres dont il est l'auteur. Cette règle est indépendante d'Express et s'appuie sur backend/src/services/permissions.ts.

Étape 6 — Requête SQL

backend/src/repositories/offers.repository.ts joint les tables offers, companies, academic_years et periods. Les résultats sont filtrés par statut ou déposant et triés par année académique puis date de création.

Étape 7 — Mapping et réponse

backend/src/mappers/offer.mapper.ts convertit les lignes SQLite en objets métier puis en DTO API. Le contrôleur renvoie le tableau JSON. Le hook reçoit les données et OffersPage les transmet notamment à frontend/src/components/OfferTable.tsx, qui les affiche.

3. Fichiers impliqués

Frontend

App.tsx, pages/OffersPage.tsx, hooks/useOffers.ts, services/offers.service.ts, models/offer.ts, utils/api.ts et components/OfferTable.tsx.

Backend

controllers/offers.controller.ts, services/offers.service.ts, services/permissions.ts, repositories/offers.repository.ts, mappers/offer.mapper.ts et models/offer.ts.

Base et vérification

backend/src/db/migrations/001_initial.sql définit la table periods. Le comportement est couvert par backend/tests/offers.test.ts et frontend/tests/OffersPage.test.tsx.

4. Ajout d'un filtre par période

Le filtre doit traverser les couches de l'interface jusqu'au SQL. Les fichiers suivants seraient concernés :

Fichier Adaptation attendue
frontend/src/pages/OffersPage.tsx Ajouter le contrôle de sélection de période et transmettre sa valeur au hook.
frontend/src/hooks/useOffers.ts Gérer la période sélectionnée et relancer le chargement lorsqu'elle change.
frontend/src/services/offers.service.ts Ajouter le paramètre de requête, par exemple ?period=P1.
frontend/src/models/offer.ts Réutiliser ou préciser le type du code de période (P1, P2, OTHER).
backend/src/controllers/offers.controller.ts Lire, valider et refuser les valeurs de période invalides avec une erreur 400.
backend/src/services/offers.service.ts Inclure la période dans le filtre transmis au repository, sans contourner la visibilité liée au profil.
backend/src/repositories/offers.repository.ts Ajouter le paramètre SQL sur p.code et le transmettre à la requête préparée.
backend/src/models/offer.ts Ajouter le type de filtre si le modèle distingue les codes de période des chaînes générales.
backend/API.md Documenter le paramètre, ses valeurs autorisées et les réponses 400.
backend/http/offers.http Ajouter un exemple de requête avec une période.
backend/tests/offers.test.ts Tester les périodes valides, invalides, répétées et la combinaison avec les droits.
frontend/tests/OffersPage.test.tsx Tester le contrôle, la requête envoyée et le rendu correspondant au filtre.
Point de sécurité : le filtre par période ne remplace pas la règle de visibilité. Le backend doit appliquer simultanément le filtre demandé et les permissions du profil ; le masquage ou le filtrage dans React ne constitue pas une protection.
Parcours basé sur l'architecture documentée dans docs/architecture.md et sur l'implémentation actuelle de la liste des offres.
